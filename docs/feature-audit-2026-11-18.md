## 현재 작업 코드에서 수정한 문제

1. **LEVEL 필터/표시 규격 불일치**
   - 기존 main 서버의 `membershipLevel`/`NONE`과 현재 코드의 `memberType`/`UNDECIDED` 차이를 처리한다.
   - 두 조회 파라미터를 함께 보내고 서버 응답을 화면에서 사용하는 형식으로 변환한다.
   - ROLE과 LEVEL의 조합, ALL, 미정, 페이지 정보 보존을 테스트했다.

2. **main 서버의 가입 대기 계정이 가입 화면을 건너뛰는 문제**
   - `registrationRequired`뿐 아니라 반대 의미의 `signupCompleted`도 읽는다.
   - 가입 대기/완료 계정의 화면 이동을 각각 검증했다.
   - 가입 정보 수정 화면은 `studentNumber` 응답도 읽어 입학 연도 두 자리로 표시한다.

3. **이름 변경 API 경로 불일치**
   - main의 `SettingController`에는 `PATCH /api/member/name`이 이미 있다. 요청과 응답은 모두 `{ "name": "이름" }` 형식이다.
   - 프론트의 `PATCH /user/me` 호출을 기존 설정 API 경로로 변경했다. 중복 이름 변경 API는 추가하지 않는다.
   - 실제 설정 API의 `name` 응답으로 화면과 로그인 표시 이름을 갱신하는 테스트를 수행한다.

4. **이름 변경 후 로그인 표시 이름이 남는 문제와 중복 저장**
   - 저장 성공 시 화면과 `authStorage`의 이름을 함께 갱신한다.
   - 저장 중 확인 버튼을 비활성화한다. 실패하면 기존 이름과 확인 창을 유지한다.

5. **이름 길이 검증 불일치**
   - 가입 화면은 4자 제한인데 서버는 50자까지 허용하던 차이를 맞췄다.
   - 가입/가입 정보 수정 서버 검증과 이름 변경 입력을 1~4자로 맞췄다. 기존 설정 API 자체는 한글 1~10자 또는 영문 1~15자를 허용하므로 프론트의 4자 제한은 더 좁은 입력 정책이다.

6. **설정 정보 조회 실패 후 빈 정보로 편집 가능한 문제**
   - 오류를 표시하고 재조회 버튼을 제공한다.
   - 조회 실패 중 이름/가입 정보 편집을 막고, 재조회 성공 시 다시 활성화한다.

7. **필터를 적용한 뒷페이지에서 회원 정보를 변경한 뒤 빈 페이지가 남는 문제**
   - 필터를 벗어날 수 있는 변경 후 첫 페이지부터 다시 조회한다.
   - 선택 목록의 변경된 LEVEL은 유지한다.

## 백엔드 통합 전에 해결해야 하는 충돌

### 1. 회원가입 저장 API와 정책이 main과 다르다

| 항목 | 현재 작업 | 조회한 main 서버 |
| --- | --- | --- |
| 최초 가입 저장 | `POST /user/registration` | `POST /user/signup` |
| 가입 정보 수정 | `PATCH /user/registration` | 해당 경로 없음 |
| 회원 여부 | `wapMember` | `member` |
| 학번 | `studentId`, 입학 연도 두 자리 | `studentNumber`, 9자리 |
| 회원 단계 | 관리자가 별도로 지정 | 회원 가입 요청에 `memberType` 필수 |
| 가입 후 ROLE | 기존 권한 유지 | 회원 가입 시 `ROLE_MEMBER`로 변경 |
| 가입 완료 표시 | `registrationRequired=false` | `signupCompleted=true` |

가입 상태 **읽기**는 호환 처리했지만 저장 요청 전체가 main과 호환된 것은 아니다. 경로만 바꾸면 학번/회원 구분/권한 정책이 달라 가입이 실패하거나 의도와 다른 권한 변경이 발생할 수 있다. 입력 정책과 서버 API를 함께 확정해야 한다.

### 2. LEVEL 저장 API와 저장 컬럼이 다르다

현재 작업은 `PATCH /admin/role/attributes`와 `member_type` 컬럼을 사용한다. main은 ROLE과 LEVEL을 개별 API로 변경하고 `membership_level` 컬럼을 사용한다. 목록 필터 호환 수정만으로 통합 저장까지 동작하는 것은 아니다. 기존 회원 단계 데이터를 어느 컬럼으로 통합할지와 통합 저장 API 배포가 필요하다.

### 3. Flyway 마이그레이션 버전 충돌

현재 추가한 `V16__add_user_member_type.sql`, `V17__add_user_registration.sql`의 번호는 main의 다음 파일과 중복된다.

- `V16__separate_membership_level_from_role.sql`
- `V17__snapshot_attendance_membership_level.sql`

그대로 합치면 Flyway 버전 중복으로 서버 기동이 실패할 수 있다. main에는 V20까지 있으므로 병합 시점의 최신 버전과 실제 적용 이력을 확인하여 새 번호/데이터 전환 방식을 정해야 한다. 이 점검에서는 이미 적용되었을 수 있는 마이그레이션 파일의 번호나 운영 DB를 변경하지 않았다.

### 4. 계정 삭제의 main 추가 데이터 정리

로컬 계정 삭제 테스트는 자기 계정/프로젝트 소유 계정 거부, 잘못된 ID 처리, 관련 레코드 삭제 순서를 확인한다. main의 V19는 `team_member.user_id`를 추가하지만 현재 삭제 서비스는 이 테이블을 정리하지 않는다. main과 합칠 때 삭제된 계정을 가리키는 팀원 정보가 남지 않도록 정책과 구현을 보완해야 한다.

## 별도 출석 브랜치에서 재현한 문제

대상 커밋: `533d05b`, `feat/702-check-in-admin-ui`.

- 생성 → 출석 상태/비고 변경 → 종료 → 결과 수정 → 삭제 시나리오 통과.
- 이름 검색 및 종료된 결과의 수정 취소 시나리오 통과.
- `role=ROLE_MEMBER`, `memberType=NEW`인 회원을 **신입 대신 정회원으로 표시하는 오류** 재현. 화면과 저장 도우미가 회원 단계를 ROLE에서 추론한다.
- 출석부/출석 상태는 브라우저 `localStorage`에 저장한다. 회원/행사 목록만 서버에서 조회하며 서버 출석 CRUD/QR API와 연결되지 않았다.
- 현재 브랜치에는 해당 화면이 없어 원본 출석 브랜치를 수정하거나 병합하지 않았다.
